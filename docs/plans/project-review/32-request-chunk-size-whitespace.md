# 32. 요청 청크 크기 뒤에 공백만 있는 줄 거절

우선순위 3 · 리뷰 ①의 문법 지적 · 구현 완료 · 기준은 `dev`의 `01a822e`에 26~29번을 반영한 작업 트리다.

## 문제와 적용 범위

청크 크기 뒤에 스페이스나 탭만 있고 이어지는 확장이 없어도 현재 파서는 그 줄을 수락한다. RFC 9112의 청크 문법에서는 크기 뒤의 구분 공백이 확장을 여는 세미콜론과 함께 올 수 있다. 이번 수정은 클라이언트 요청의 데이터 청크와 마지막 0 청크에서 공백만 남은 줄을 400으로 처리하는 데 한정한다. 유효한 확장의 8,192바이트 한도는 28번에서 정한 별도 규칙이다. [청크 문법](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1.1) · [28번의 합산 기준](28-request-chunk-extension-limit.md)

## 구현 순서

1. `read_chunked_request()`에서 공유 크기 파서가 성공한 직후, 확장 길이가 0이고 CRLF를 뺀 줄의 마지막 문자가 스페이스 또는 탭이면 400을 반환한다. 청크 데이터나 마지막 트레일러를 읽기 전에 판정을 끝낸다. 요청을 읽는 쪽에서 이 조건을 적용하면 백엔드 응답 중계와 `Transfer-Encoding` 파싱에 영향이 없다. [요청 본문 처리](../../../src/http_request.c) · [공유 프레이밍 파서](../../../src/http_framing.c)
2. 28번의 경계값 테스트에서 확장이 없는 중간 청크를 유효한 크기 표기 `01`로 바꾼다. 선행 0은 크기 숫자의 일부다. 유효한 세미콜론 앞의 구분 공백, 인용된 확장 값, 마지막 청크의 확장은 기존 합산 기준을 적용한다.

## 완료 기준과 최소 검증

기존 `check_chunk_error()`에 데이터 청크와 마지막 0 청크에서 각각 공백 또는 탭만 남은 사례를 넣어 둘 다 400인지 확인한다. 같은 바이너리에서 `01`의 본문을 정상적으로 읽고, 유효한 확장의 합계가 8,192바이트면 수락하고 8,193바이트면 413을 반환해야 한다. 구현 후 Linux Docker에서 `test_http_request`만 한 번 실행한다. [요청 파서 테스트](../../../tests/test_http_request.c)

## 반영 결과

Linux Docker(`gcc:14`)에서 `test_http_request`가 통과했다. 데이터 청크의 크기 뒤에 스페이스만 있거나 마지막 0 청크 뒤에 탭만 있으면 400을 반환했다. `01`로 표시한 청크의 본문은 정상적으로 읽었고, 확장의 합계가 8,192바이트일 때는 수락하고 8,193바이트일 때는 413을 반환했다.
