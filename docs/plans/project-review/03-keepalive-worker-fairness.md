# 03. 대기 중인 연결에 워커를 양보할 시점 정하기

**작업 유형** · 정책 설계. 작은 응답의 송신 지연과 헤더 수신 마감은 각각 01, 02에서 다룬다.

워커는 연결 하나를 맡아 다음 요청까지 기다린다. 따라서 정상적인 유휴 연결도 워커를 점유할 수 있다. 정적 응답은 keep-alive가 가능하고, CGI와 프록시 응답은 이미 연결을 닫는다. [연결 처리 루프](../../../src/server.c) · [워커 큐](../../../src/threadpool.c)

1. 두 상황을 구분한다. 응답을 보내려는 시점에 큐에 연결이 있으면 현재 워커가 연결을 양보할 수 있다. 모든 워커가 이미 유휴 읽기에 들어간 뒤 새 연결이 들어오면 응답 시점의 큐 확인만으로는 워커를 깨울 수 없다.
2. 우선 검토할 정책은 전자의 경우에만 다음 연결에 차례를 주는 방식이다. 큐 상태는 풀의 잠금 안에서 읽고 소켓 I/O 전에 잠금을 해제한다. 닫기로 결정하면 헤더 생성 전에 `req.keep_alive`에 반영해 실제 종료 동작과 `Connection` 값을 맞춘다.
3. 후자의 경우에도 즉시 서비스를 보장해야 하는지는 별도 설계 결정으로 남긴다. 유휴 소켓의 소유권을 이관하는 구현은 종료 처리, RIO에 남은 데이터, FD를 닫을 주체까지 함께 설계해야 한다.

**완료 기준과 최소 검증** · 현재 단계의 결과물은 두 상황에서의 예상 동작과 정책 채택 여부다. 코드 흐름을 대조하면 이 설계 검토는 끝난다. 이후 완화책을 채택할 때만 대기 연결이 있는 정적 응답의 종료 헤더와 다음 요청의 처리 순서를 한 사례로 확인한다.

## 검토 결과

정적 응답은 기존 keep-alive 정책을 유지한다. 큐 길이만 보고 연결을 끊는 정책은 보류한다. 작업을 넣은 직후에는 빈 워커가 깨어나기 전에도 큐 길이가 양수일 수 있어서, 정상적으로 재사용할 연결까지 닫게 된다.

워커가 모두 유휴 읽기에 들어간 상태에서는 새 연결을 넣을 때 풀의 조건 변수를 깨워도 소켓 입력을 기다리는 워커에게는 전달되지 않는다. 이때 새 연결은 워커가 돌아올 때까지 대기한다. 유휴 제한 5초는 각 연결의 다음 요청을 기다리는 시간이며 큐 전체의 대기 시간 상한을 보장하지 않는다. 새 연결의 최대 대기 시간을 요구사항으로 정하면, 처리 가능한 워커 수와 유휴 소켓의 소유권을 함께 다루는 설계로 다시 검토한다.

## 후속 변경 (정책 채택)

위에서 지적한 "제출 직후 큐 길이가 양수" 문제는 큐 길이 대신 **쉬는 워커 수보다 큐 길이가 클 때만** 대기로 세는 방식으로 피했다. 풀은 조건 변수에서 잠든 워커 수(`idle`)를 세고, `threadpool_has_waiting()`은 `count > idle`을 잠금 안에서 반환한다. 쉬는 워커가 가져갈 작업은 깨어나기 전에도 대기로 세지 않는다.

1. 응답 직전: 대기 연결이 있으면 그 응답을 `Connection: close`로 보내고 연결을 넘긴다.
2. 다음 요청 대기 중: 소켓을 50ms 단위로 기다리며, 100ms 이상 유휴이고 대기 연결이 있으면 유휴 연결을 닫는다. 종료 신호도 같은 주기로 확인해 SIGTERM 후 종료가 4.6초에서 17ms로 줄었다.

`ab -k -n 5000`에서 동시 9 연결의 최장 지연은 5,003ms에서 6ms로, 동시 32 연결은 10,138ms·실패 14건에서 8ms·실패 0건으로 바뀌었다. 검증: `test_threadpool`, `functional.sh`의 워커 1개 서버 사례.
