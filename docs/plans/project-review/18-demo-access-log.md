# 18. 시연에서 백엔드 선택과 503을 확인할 수 있는 접근 로그 추가하기

**반영 결과**

`-v`로 켜는 접근 로그를 추가했다. `functional.sh`에서 라운드로빈, 장애 전환, 큐 초과 503, 200 헤더 이후 본문 중단, 쿼리 생략과 기본 로그 꺼짐을 확인했다.

현재 stderr에는 기동 오류와 큐 크기 경고 등이 기록된다. 요청 처리는 성공을 0으로 반환하므로 이 값만으로 클라이언트에 보낸 HTTP 상태를 알 수 없다. 또한 큐가 가득 찼을 때는 요청 라인을 읽기 전에 수락 루프가 503을 직접 전송한다. 두 경로가 시연에서 보이도록 로그 범위를 정한다. [요청 처리와 과부하 분기](../../../src/server.c) · [프록시 중계](../../../src/proxy.c)

## 확정 범위

기본값은 로그 꺼짐으로 하고, CLI의 `-v`로 시연용 stderr 출력을 켠다. 처리한 요청마다 메서드, 쿼리를 뺀 경로, 전송한 최종 상태 코드, 완료·중단 여부를 한 줄에 기록한다. Reverse Proxy 요청에는 처음 시도한 백엔드, 최종 연결한 백엔드, 실제 연결 시도 횟수도 넣는다. 이 정보만으로 라운드로빈과 개별 요청의 장애 전환을 설명할 수 있다.

요청을 파싱하기 전에 거절하면 과부하 거절임을 기록하고 메서드와 경로는 빈 값으로 남긴다. 503 전송 자체가 실패했으면 전송 실패로 표시한다. 본문, 쿼리, 요청 헤더는 기록 대상에서 제외한다.

## 구현 순서

1. CLI와 서버 설정에 로그 플래그를 연결한다. 워커는 요청별 기록을 만들고, 정적·CGI·프록시 경로가 최종 응답 헤더를 보낸 시점에 실제 상태를 기록한다. 오류 응답으로 전환된 경우에도 최종 상태 하나만 남긴다. 헤더가 끝나기 전 전송 실패와 200을 보낸 뒤 본문이 잘린 경우를 구분한다. [CLI](../../../src/main.c) · [로컬 응답](../../../src/http_response.c) · [중계 응답](../../../src/response_stream.c)
2. Reverse Proxy의 연결 시도 지점에서 백엔드 정보를 채운다. 정상 요청은 처리 종료 시, 큐 초과는 수락 루프의 거절 처리 시 한 번만 출력한다. 줄 길이를 제한하고 경로 내 제어 문자를 이스케이프해 여러 워커가 기록해도 요청별 한 줄을 읽을 수 있게 한다.
3. README에 옵션과 로그 예시를 추가한다. 서로 다른 백엔드로 간 정상 요청, 첫 후보 실패 후 두 번째 후보에서 끝난 요청, 파싱 전 큐 초과를 예로 든다.

## 완료 기준과 최소 검증

기존 기능 검사에서 로그를 켠 프록시와 작은 큐 서버의 stderr를 임시 파일로 받는다. 두 백엔드가 번갈아 선택된 요청, 첫 후보 실패 후 200으로 끝난 요청, 큐 초과 503 한 줄의 필드를 확인한다. 장애 전환 검사는 다음 첫 후보가 중지된 서버가 되도록 라운드로빈 순서를 고정한다. 같은 기능 검사에 이미 있는 로그 꺼짐 서버로 기본 동작도 확인한다. 별도 부하 실행은 필요하지 않다. [기능 검사](../../../tests/functional.sh)
