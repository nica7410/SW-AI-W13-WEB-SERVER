# 25. 프록시 라우팅과 HTTP 호환성 개선

기준 커밋은 `5f211d5`다. 아래 표는 2026년 11월 23일 작업 트리에 적용한 순서와 검증 결과를 기록한다.

| 순서 | 목표 | 반영 결과와 근거 |
|---|---|---|
| 1 | 프록시 순환을 끊고 정상 백엔드를 계속 사용한다. | 프록시를 거칠 때 수신 주소와 포트를 Via에 남긴다. 라우팅 후보와 연결된 소켓의 실제 목적지를 확인해 순환 후보에는 요청 본문을 보내지 않는다. 직접 감지한 순환 후보만 남으면 508, 다른 후보가 연결을 거부하면 502, 연결 시간이 만료되면 504를 반환한다. [프록시](../../../src/proxy.c) |
| 2 | 자기 서버를 가리키는 절대 URI도 기존 경로 규칙으로 처리한다. | 수신 포트와 로컬 IP·호스트 이름을 대조한다. 운영 도메인은 `-n`으로 지정할 수 있다. 정적 파일, CGI, Reverse 라우팅에 같은 규칙을 적용하고 백엔드에는 URI에서 얻은 Host와 경로·쿼리를 전달한다. [요청 분기](../../../src/server.c) |
| 3 | 과제의 설계 선택과 측정 근거를 설명한다. | README에 TCP 수락 과정, 동시성 모델별 비용, C10K에서의 자원 한계, 두 프록시의 용도를 정리했다. 기준 커밋 CI와 Docker에서 직접 확인한 세 가지 동작을 구분하고 과거 성능·메모리 수치의 측정 버전을 표시했다. [설계와 검증](../../../README.md) |
| 4 | HTTP/1.1 클라이언트와 백엔드의 호환 범위를 넓힌다. | chunked 요청 본문을 1MiB·5초 상한 안에서 디코딩한다. CGI와 프록시는 기존 본문 처리 경로를 사용한다. 103 Early Hints는 최종 응답에 앞서 필드와 함께 중계한다. [요청 파서](../../../src/http_request.c) · [응답 중계](../../../src/response_stream.c) |
| 5 | macOS CGI의 검증 대상과 실행 대상을 일치시킨다. | 비공개 임시 하드 링크의 장치·inode를 열린 파일과 대조하고, 일치하는 링크만 실행한다. 실행이 끝나면 링크를 해제한다. [CGI 처리](../../../src/cgi.c) |

## 작업 트리 검증

- Linux Docker `gcc:14`에서 `-Wall -Wextra -Werror`로 서버를 빌드했다.
- `test_http_request`가 이진 chunked 본문, 트레일러 뒤 다음 요청, 길이 충돌, 크기 상한, 잘못된 조각 경계를 확인했다. [파서 검사](../../../tests/test_http_request.c)
- `test_proxy_relay`가 103의 Link 전달과 연결 전용 헤더 제거, 뒤따르는 최종 응답과 본문의 경계를 확인했다. [중계 검사](../../../tests/test_proxy_relay.c)
- `functional.sh`가 로컬 절대 URI의 정적·CGI·Reverse 처리, 외부 Forward 제한, 자기 자신과 두 프록시 사이의 순환, 순환과 연결 거부가 섞인 경로, chunked POST의 Forward 전달을 확인했다. [기능 검사](../../../tests/functional.sh)
- macOS에서 사용하는 POSIX CGI 분기를 Linux에서 별도로 빌드해 `test_server_edges`를 실행했다. 정상 실행, 실행 권한 거부, 파일 교체 후 403이 통과했다. 이 변경의 macOS 네이티브 실행은 아직 확인하지 못했다. [CGI 검사](../../../tests/test_server_edges.c)
