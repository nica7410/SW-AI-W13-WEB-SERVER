# 22. Reverse Proxy가 확인한 접속자 주소와 프로토콜 전달하기

선택 작업 · 백엔드에서 접속자를 식별하는 시연 · 외부 제안 3번 · 기준 커밋 `fb656d0` · 구현 완료

**반영 결과**

Reverse Proxy가 클라이언트 소켓에서 확인한 숫자 IP와 `http`를 기록한다. `test_proxy_relay`에서 로컬 TCP 요청의 중복·혼합 대소문자 헤더가 대체되고 Forward 요청에는 두 헤더가 추가되지 않는 것을 확인했다.

현재 공통 요청 작성기는 일반 요청 헤더를 백엔드로 복사한다. 따라서 클라이언트가 보낸 `X-Forwarded-For`가 이미 있을 수 있다. 이 프로젝트의 Reverse Proxy가 클라이언트와 직접 HTTP로 연결된다는 조건에서, 자신이 확인한 두 값의 출처를 분명하게 만든다. [공통 요청 작성기](../../../src/proxy.c) · [Forward Proxy 호출 경로](../../../src/forward_proxy.c)

## 작업 범위와 순서

1. Reverse Proxy에서 클라이언트 소켓의 TCP 상대 주소를 `getpeername()`으로 읽고 숫자 IP로 변환한다. 역방향 DNS 조회는 필요 없다. 이 값은 바로 앞 연결 상대를 가리킨다. 여러 신뢰 프록시를 거쳐 최초 사용자를 추적하는 구성은 별도 문제다.
2. Reverse 요청을 쓸 때 두 헤더 이름을 대소문자 구분 없이 걸러 기존 값과 중복을 제거한다. 이어 `X-Forwarded-For`에는 확인한 IP를, `X-Forwarded-Proto`에는 이 서버가 직접 받은 `http`를 각각 한 번 쓴다. 주소를 얻을 수 없으면 IP 헤더를 생략하고 중계한다.
3. 공통 중계 함수에 Reverse 경로가 확인한 정보만 전달한다. Forward Proxy 호출은 기존 전달 규칙을 사용한다. README에는 직접 접속한 클라이언트의 주소가 백엔드에 보이는 예시 하나를 넣는다.

## 완료 기준과 최소 검증

기존 `test_proxy_relay`의 백엔드 수신 요청 검사를 확장한다. Reverse 사례에는 로컬 TCP 클라이언트를 사용해 요청에 임의로 지정한 두 헤더가 실제 접속 주소와 `http`로 각각 한 번 대체되는지 확인한다. 같은 실행 파일의 Forward 사례에서 Reverse 전용 헤더가 새로 생기지 않는지도 확인한다. 해당 실행 파일 한 번이 검증 범위다. [프록시 중계 검사](../../../tests/test_proxy_relay.c)
