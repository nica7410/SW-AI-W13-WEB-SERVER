# 26. 다른 인터페이스로 돌아온 프록시 요청 감지

구현 계획 · 우선순위 1 · 리뷰 ④의 다중 인터페이스 항목 · 기준 커밋 `01a822e`

## 문제와 범위

현재 프록시는 요청을 전달할 때 수신 소켓의 IP와 포트를 `Via`에 기록한다. 같은 프로세스가 다른 로컬 IP로 요청을 다시 받으면 `via_revisits_listener()`의 문자열 비교가 이전 홉을 놓친다. 목표는 **워커가 재진입한 요청을 읽었을 때 다음 백엔드에 연결하기 전에 508을 반환하는 것**이다. 이미 워커 큐에서 기다리는 시간은 이 판정의 적용 구간 밖이다. [수신 주소 비교](../../../src/proxy_identity.c) · [Forward 진입점](../../../src/forward_proxy.c) · [Reverse 진입점](../../../src/proxy.c)

## 구현 순서

1. 서버 인스턴스마다 시작 시 한 번 생성해 워커들이 공유하는 식별자를 둔다. 프로세스별 임의 값으로 생성하면 호스트 이름과 리스닝 포트가 같은 서로 다른 인스턴스도 구별할 수 있다.
2. 전달 **요청**의 Via 항목에는 기존 `received-by` 주소와 함께 해당 식별자를 정해진 형식의 HTTP 주석으로 기록한다. 수신 측은 각 Via 필드와 쉼표 목록을 순회해 온전한 항목에 붙은 자체 형식의 주석을 판독한다. 식별자는 홉 비교에만 사용한다. 기존 숫자 주소는 다음 목적지를 연결 직후 대조하는 데 계속 필요하다. 중간 서버가 주석을 제거한 경로에서는 기존 주소 비교가 적용된다. [요청 작성과 연결 후 검사](../../../src/proxy.c) · [Via 문법과 주석 처리](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.6.3)
3. Forward·Reverse의 기존 진입 검사에 자기 식별자 일치를 추가한다. 다른 인스턴스가 남긴 주석이나 주석 본문의 일부 문자열을 일치로 세지 않는다. 이 작업은 절대 URI의 로컬 주소 정책과 독립적이다.

## 완료 기준과 최소 검증

기존 프록시 중계 검사에서 실제 TCP 소켓으로 생성된 Via 항목을 얻는다. 다음 입력은 이전 홉의 주소만 다른 주소로 표현하고 같은 식별자를 보존한다. Reverse 연결 대역의 호출 횟수 0과 반환값 508을 함께 확인한다. 같은 소켓에서 외부 홉의 주소와 별도 식별자를 사용한 대조 요청은 정상 전달돼야 한다. 네트워크 인터페이스 추가나 연결 부하 없이 판정 지점을 확인할 수 있다. 해당 테스트 바이너리만 한 번 실행한다. [프록시 중계 테스트](../../../tests/test_proxy_relay.c)

## 반영 결과

Forward와 Reverse가 전달하는 Via 주석에 서버 시작 때 생성한 128비트 식별자를 넣었다. 난수 장치를 읽을 수 없으면 시작 로그에 경고를 쓰고 수신 주소로 순환을 검사한다. Linux Docker(`gcc:14`)의 `test_proxy_relay`에서 실제 TCP 요청에 붙은 식별자를 보존하고 주소만 바꾸자 508과 백엔드 연결 시도 0회를 확인했다. 다른 식별자와 중첩 주석 안의 식별자를 보낸 대조 요청은 백엔드에 한 번 전달됐다.
