# 21. 접근 로그에 요청을 읽은 뒤의 처리 시간 기록하기

우선 작업 3 · 외부 제안 6번 · 기준 커밋 `fb656d0` · 구현 완료

**반영 결과**

`-v` 접근 로그 끝에 단조 시계로 측정한 `duration_ms`를 추가했다. `functional.sh`에서 정상·중단·503의 로그 형식과 무응답 백엔드의 504에 대기 시간이 포함되는 것을 확인했다.

현재 `attempts=2`는 백엔드를 두 번 시도했다는 뜻이다. 두 번째 후보로 즉시 넘어간 요청과 첫 후보에서 오래 기다린 요청은 같은 모양으로 기록된다. 시연에서는 한 줄에 `duration_ms`를 함께 표시해 재시도 횟수와 처리 시간을 같이 읽게 한다. [로그 구현](../../../src/access_log.c) · [기존 로그 예시](../../../README.md#접근-로그로-분산과-장애-전환-확인하기)

## 작업 범위와 순서

1. 일반 요청은 `read_request()`가 반환한 뒤 `access_begin()`부터 `access_finish()`까지 측정한다. 이 구간에는 라우팅, 백엔드 연결, 응답 송신과 로그 직전의 정리가 포함된다. 큐에서 기다린 시간과 요청 수신 시간은 측정 구간 밖이다. 큐 초과 거절은 수락 스레드에서 503 전송을 시도하는 구간을 잰다. [두 로그 경로](../../../src/server.c)
2. 활성화된 요청의 스레드별 기록에 시작 시각을 저장하고, 같은 단조 시계로 얻은 차이를 밀리초 정수로 출력한다. 기존 `deadline_after(0)`가 단조 시계의 현재 밀리초를 제공한다. `-v`가 꺼져 있으면 로그를 위한 시계 조회를 건너뛴다. [시계 구현](../../../src/deadline.c)
3. 기존 한 줄의 마지막에 `duration_ms`를 붙이고 README 예시에 측정 시작·종료 지점을 설명한다. 이번 시연에서 필요한 값은 경과 시간 한 가지로 정한다.

## 완료 기준과 최소 검증

기존 `functional.sh`의 로그 비교에서 고정 필드는 그대로 확인하고 마지막 값만 0 이상의 정수로 검사한다. 이미 있는 무응답 백엔드의 504 기록으로 기다린 시간이 반영되는지 확인하고, 정상 응답과 큐 초과 503은 0ms도 허용한다. 이 스크립트 한 번으로 검증한다. [기능 검사](../../../tests/functional.sh)
