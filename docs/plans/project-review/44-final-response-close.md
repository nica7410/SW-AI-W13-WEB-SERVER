# 44. 마지막 응답을 보낸 TCP 연결 정리

기준 `dev@37a55e8` · 우선순위 1 · 리뷰 1 · 반영 완료

## 작업 범위

`handle_connection()`은 요청 분기 전에 입력 정리 시간을 정한다. 이후 CGI나 프록시가 연결 종료를 선택하면 이 값이 0인 채로 마지막 응답을 보내고 소켓을 닫을 수 있다. 클라이언트가 이미 보낸 데이터가 커널에 남아 있으면 첫 응답의 일부가 유실될 수 있다. 목표는 서버가 완료한 마지막 응답을 클라이언트가 끝까지 받게 하는 것이다. [연결 처리](../../../src/server.c) · [RFC 9112 §9.6](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.6)

## 구현 순서와 경계

1. 응답을 마치는 공통 지점에서 핸들러가 확정한 연결 재사용 여부, 서버 종료 상태, 실제 송신 결과를 함께 본다. 오류 상태를 HTTP 응답으로 정상 전송한 경우도 같은 판단을 거친다. CGI·Forward·Reverse는 이 공통 경로를 사용한다.
2. 마지막 응답을 온전히 썼으면 `linger_close_input()`으로 송신 방향을 먼저 닫고, 상대의 EOF 또는 짧은 마감까지 남은 입력을 소비한다. 일반 종료의 상한은 기존 워커 양보에 쓰는 50ms를 재사용하고, 파서 거절의 기존 상한 250ms와 서버 종료 유예를 존중한다. 동일 연결에서 이 절차는 한 번만 수행한다. [기존 오류 응답 종료 정책](31-yielded-error-response-close.md) · [마감 계산](../../../src/deadline.c)
3. 재사용하는 연결은 다음 요청을 읽는다. 송신 자체가 실패한 연결은 중단 처리하고, 수락 스레드의 과부하 503은 기존 전용 정리 경로로 보낸다.

## 완료 기준과 최소 검증

실제 TCP 서버를 기동하는 기존 종료 테스트 파일에 정상 CGI 종료 사례 한 건을 독립 함수로 추가한다. 후속 입력이 커널에 남아 있는 조건에서 큰 CGI 응답을 받아, 첫 응답의 상태와 `Connection: close`, 선언한 길이, 수신한 본문의 내용과 정상 EOF를 확인한다. 유실된 바이트 수나 정확한 종료 시간은 판정 기준으로 삼지 않는다. CGI가 설정된 실제 서버를 거쳐야 요청 분기와 최종 종료 판단을 함께 검사할 수 있다. [기존 서버 기동 예제](../../../tests/test_shutdown.py)

구현 후 Windows의 Linux Docker에서 해당 함수만 한 번 실행한다. 두 프록시가 같은 마무리 지점에 도달하는 것은 호출 경로로 확인한다.

## 반영 결과

일반 종료와 워커 양보에는 최대 50ms, 파싱 거절에는 기존 250ms를 적용한다. Linux Docker에서 `test_completed_cgi_close()` 한 건을 실행했다. CGI 처리 중 후속 요청이 도착한 연결에서 200, `Connection: close`, 선언한 1,179,648바이트의 본문 전체와 정상 EOF를 확인했다. Forward·Reverse도 `dispatch()` 뒤 같은 마무리 경로에 도달한다.
