# 28. 요청 한 건의 청크 확장 길이 합계 제한

구현 계획 · 우선순위 3 · 리뷰 ⑦의 chunk extension 항목 · 기준 커밋 `01a822e`

## 문제와 한도

현재 요청 파서는 청크 줄 하나를 8KiB, 디코딩한 본문을 1MiB, 본문 수신 시간을 5초로 제한한다. 각 줄이 유효해도 여러 청크에 붙은 확장 정보의 길이 합계에는 기준이 없다. RFC 9112는 요청 단위로 확장의 총길이를 제한하고 초과하면 적절한 4xx를 보내도록 권고한다. [청크 요청 읽기](../../../src/http_request.c) · [RFC 9112 §7.1.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1.1)

**프로젝트 기본값은 요청당 8KiB(8,192바이트), 초과 응답은 413으로 정한다.** 8KiB는 이 과제 서버가 선택한 총량이다. 각 유효한 확장에서 첫 세미콜론 앞의 구분 공백부터 줄 끝까지 실제 수신한 바이트를 센다. 세미콜론·구분 공백·인용 문자열은 포함하고, 크기 숫자·줄 끝 CRLF·데이터·트레일러는 각각의 기존 규칙으로 처리한다. 확장이 없는 줄의 기여분은 0이다. 마지막 크기 0인 청크의 확장도 합산한다.

## 구현 순서

1. 요청과 응답이 공유하는 청크 크기 파서에서 확장 문법을 확인할 때, 요청 측이 그 구간의 바이트 수도 얻을 수 있게 한다. 응답 중계 호출은 기존처럼 크기와 유효성만 사용한다. [공유 프레이밍 파서](../../../src/http_framing.c) · [응답 중계](../../../src/response_stream.c)
2. 누적 상태는 `read_chunked_request()`가 처리하는 요청 한 건에 둔다. 줄의 문법을 확인한 직후 확장 길이를 잔여 예산과 비교한다. 정확히 8,192바이트까지 수락하고 초과하면 해당 청크 데이터나 트레일러를 읽기 전에 413을 반환한다. 기존 본문 해제·오류 응답·연결 종료 경로를 사용한다.
3. README의 chunked 요청 설명에 본문과 확장의 한도를 각각 표시한다. 이번 변경의 대상은 클라이언트가 보낸 청크 확장이다.

## 완료 기준과 최소 검증

기존 파서 테스트에 여러 유효한 줄로 구성한 경계값 한 쌍을 추가한다. 마지막 0 청크의 확장을 포함해 합계가 한도와 같으면 정상 종료하고, 같은 구성에서 확장 값 한 바이트만 늘리면 413이 돼야 한다. 두 경우 모두 각 줄과 디코딩한 본문은 기존 한도 안에 둔다. 기존 이진 본문·트레일러·다음 요청 경계 사례도 같은 바이너리에 들어 있다. 27번과 함께 반영하면 `test_http_request` 한 번으로 확인한다. [청크 파서 테스트](../../../tests/test_http_request.c)

## 반영 결과

공유 프레이밍 파서가 유효한 확장의 바이트 수를 돌려주고 요청 파서가 청크마다 남은 한도를 차감하도록 수정했다. Linux Docker(`gcc:14`)에서 27번과 같은 `test_http_request` 실행으로 확인했다. 마지막 0 청크까지 합계가 8,192바이트이면 본문 `xy`를 읽었고, 8,193바이트이면 트레일러 종결을 기다리지 않고 413을 반환했다.
