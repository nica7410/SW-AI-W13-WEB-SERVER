# 30. Connection이 Content-Length를 지명한 응답 거절

우선순위 1 · 리뷰 ② · 구현 완료 · 기준은 `dev`의 `01a822e`에 26~29번을 반영한 작업 트리다.

## 문제와 적용 범위

원 서버의 최종 응답에 `Content-Length`가 있고 `Connection`이 그 필드를 지명하면, 프록시는 길이를 이용해 본문을 읽으면서 클라이언트에 전달할 헤더에서는 길이를 제거한다. 원 서버가 일찍 연결을 닫았을 때 프록시는 본문 부족을 감지해도, 클라이언트는 마지막 응답의 정상 종료와 구별하기 어렵다. CGI 출력도 같은 경로를 거친다. RFC는 중계할 때 지명된 필드를 제거하도록 규정한다. 이 서버는 모순된 입력을 최종 응답 송신 전에 거절하는 정책을 택한다. [응답 검사와 중계](../../../src/response_stream.c) · [RFC 9110 §7.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.6.1)

## 구현 순서

1. `response_until()`에서 최종 응답 헤더를 모두 읽은 뒤, 실제 `Content-Length` 필드를 검사하는 분기에 기존 `connection_field()` 판정을 추가한다. 이 함수가 모든 `Connection` 필드의 쉼표 목록을 대소문자 구분 없이 검사하므로 필드 순서에 의존하지 않는다.
2. 두 조건이 함께 성립하면 기존 오류 반환 경로를 사용한다. Forward·Reverse의 원 서버 응답은 502, CGI 출력은 500이다. 이 검사는 최종 상태 줄 송신과 HEAD 본문 생략보다 앞에 둔다. `Connection`에 이름만 있고 실제 길이 필드가 없는 응답에는 이 규칙을 적용할 이유가 없다.

## 완료 기준과 최소 검증

기존 `test_proxy_relay`의 소켓 쌍으로 원 서버 응답과 CGI 출력 각 한 건을 검사한다. CGI 입력에는 정상 `Content-Type`을 넣어 500의 원인을 구분한다. 입력 중 한 건은 길이 필드 뒤에 `Connection`을 배치하고 혼합 대소문자 목록으로 지명한다. 기대값은 각각 502와 500이며, 중계 함수가 반환할 때 클라이언트 쪽에 최종 상태 줄이나 본문이 기록된 바이트 수는 0이다. 일반 길이 응답은 같은 바이너리의 기존 성공 사례로 확인한다. 구현 후 Linux Docker에서 `test_proxy_relay`만 한 번 실행한다. [중계 테스트](../../../tests/test_proxy_relay.c)

## 반영 결과

Linux Docker(`gcc:14`)에서 `test_proxy_relay`가 통과했다. 유효한 길이 필드를 뒤쪽 `Connection` 목록에서 혼합 대소문자로 지명한 경우, 중계 함수가 원 서버 응답에는 502, CGI 출력에는 500을 반환했다. 두 소켓 모두 클라이언트에 기록된 바이트 수는 0이었다.
