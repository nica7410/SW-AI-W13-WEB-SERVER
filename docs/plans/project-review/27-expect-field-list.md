# 27. 반복된 Expect 필드를 일관되게 처리하기

구현 계획 · 우선순위 2 · 리뷰 ⑤의 Expect 항목 · 기준 커밋 `01a822e`

## 문제와 처리 정책

`read_request()`가 첫 번째 Expect 값만 확인하므로, 지원하는 값과 미지원 값이 서로 다른 필드에 있으면 순서에 따라 결과가 바뀐다. HTTP에서 Expect는 목록 필드다. 이 서버는 미지원 기대값에 417을 보내는 기존 정책을 모든 항목에 적용한다. 417은 이 프로젝트가 선택한 응답이다. [요청 파서](../../../src/http_request.c) · [RFC 9110 §10.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.1.1)

| 입력 | 목표 동작 |
|---|---|
| Expect 필드 없음 | 기존 요청 본문 처리 |
| 한 줄 또는 여러 줄에 `100-continue`만 반복 | 대소문자와 주변 공백을 허용한다. HTTP/1.1에서 이미 본문을 받을 조건이면 100을 한 번 보낸다. |
| 지원 값과 미지원 값이 섞임 | 줄의 순서와 한 줄로 합쳐졌는지에 관계없이 417을 반환한다. 100 송신과 본문 읽기에 앞서 결정한다. |
| Expect 필드는 있으나 목록 전체에 기대값이 없음 | 기존 빈 Expect에 대한 417 정책을 적용한다. 정상 항목 옆의 빈 목록 원소는 건너뛴다. |

## 구현 순서

1. 헤더 경계와 본문 프레이밍을 검사한 후 모든 Expect 필드의 목록을 평가한다. 지원 토큰은 대소문자를 무시해 정확히 일치하는 `100-continue`다. 전부 확인한 뒤에만 중간 응답 여부를 결정한다.
2. HTTP/1.0과 길이 0인 고정 길이 본문에는 기존처럼 100을 보내지 않는다. HTTP/1.1 chunked 요청은 본문 수신 대상으로 처리한다. 실제로 앞단이 보낸 100과 백엔드가 보낸 100의 중복 억제 조건도 함께 대조한다. [중간 응답 처리](../../../src/response_stream.c)

## 완료 기준과 최소 검증

기존 `test_expect()`의 소켓 검사를 재사용한다. 지원 값 반복 시 중간 응답의 전체 바이트가 100 한 건과 일치해야 한다. 지원·미지원 값을 두 순서로 배치한 입력은 모두 417이고, 중간 응답 바이트는 0이어야 한다. 한 입력을 쉼표 목록으로도 표현해 반복 필드와 같은 의미인지 확인한다. 28번과 함께 적용할 때는 두 변경 후 `test_http_request`를 한 번 실행한다. [Expect 테스트](../../../tests/test_http_request.c)

## 반영 결과

모든 Expect 필드와 쉼표 목록을 본문 처리 전에 검사하도록 수정했다. Linux Docker(`gcc:14`)의 `test_http_request`에서 지원 값 반복 시 중간 응답 한 건, 지원·미지원 혼합 시 순서에 관계없이 417과 중간 응답 0바이트를 확인했다. 전체가 빈 목록, HTTP/1.0, 길이 0인 요청, chunked 요청도 같은 검사에서 확인했다. 중계 경로는 검사를 통과한 요청만 받아 기존 조건으로 백엔드의 중복 100을 걸러낸다.
