# 49. 접근 로그에 요청 수신 시간 기록

기준 `dev@37a55e8` · 후속 작업 3 · 리뷰 6-1 · 반영 완료

## 작업 범위

현재 `duration_ms`는 요청을 읽은 뒤부터 응답 처리와 정리가 끝날 때까지다. 느린 업로드와 느린 응답 처리를 한 요청의 로그에서 구분할 수 있도록 `-v`의 일반 요청 기록에 `request_read_ms` 한 필드를 추가한다. 이 측정에는 큐나 스레드 풀 인터페이스 변경이 필요하지 않다. [요청 처리](../../../src/server.c) · [로그 구현](../../../src/access_log.c) · [기존 시간 정의](21-access-log-duration.md)

## 구현 순서와 경계

1. 워커가 첫 바이트의 준비를 확인한 뒤 `read_request()`에 진입하기 직전과 반환 직후의 단조 시계 차이를 밀리초로 기록한다. 따라서 헤더·본문 수신 및 파싱이 포함되고, 큐 대기와 유휴 keep-alive 대기는 제외된다. `-v`가 꺼져 있으면 추가 시계 조회도 생략한다.
2. 기존에 기록하는 요청에만 새 값을 붙인다. 파싱 오류도 실제 읽은 시간을 사용하고, 요청을 읽기 전 거절한 `event=overload`는 기존 형식으로 둔다. `duration_ms`, `attempts`, `outcome`의 의미를 보존하고 README의 예시와 필드 정의를 갱신한다.
3. 기존 기능 검사는 줄 끝의 `duration_ms`를 숫자로 읽는다. 요청 로그의 새 필드를 반영하도록 비교식을 조정하되, 기존 필드와 504 대기 시간 검사는 계속 확인한다. [로그 형식 검사](../../../tests/functional.sh)

## 완료 기준과 최소 검증

Linux Docker에서 `-v` 서버 한 대에 정상 POST 한 건을 보낸다. `100 Continue`를 받은 뒤 짧은 간격을 두고 본문을 마치면, 그 간격이 실제 수신 구간에 포함됐음을 확인할 수 있다. 해당 로그 한 줄에서 `request_read_ms`가 그 간격을 반영하고 `duration_ms`도 별도 정수로 기록되는지 확인한다. 정확한 시간 일치나 두 값의 대소 관계는 요구하지 않는다. 기존 로그 비교식은 이 한 줄과 기존 503 예시로 확인한다. 전체 기능 테스트나 부하 측정은 이 변경의 최소 검증에 포함하지 않는다.

## 반영 결과

Linux Docker에서 `100 Continue` 후 본문을 80ms 뒤에 완료한 CGI POST 한 건이 200을 반환했다. 해당 로그는 `duration_ms=2 request_read_ms=80`이었다. `functional.sh`의 로그 비교식도 이 요청과 기존 503 형식의 예시 한 줄을 각각 인식했다.
