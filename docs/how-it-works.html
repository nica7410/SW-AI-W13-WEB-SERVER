웹서버의 구조는 손님을 받는 식당과 비슷합니다. 접수 창구 한 곳이 손님을 받아 번호표를 주고, 정해진 수의 요리사가 번호 순서대로 손님을 맡습니다. 각 칸의 아래 줄은 그 역할을 맡은 실제 함수입니다.

요청의 여정

요청 하나가 응답이 되기까지

curl http://127.0.0.1:8080/index.html을 보냈을 때 서버 안에서 일어나는 일을 순서대로 적었습니다.

  1. 서버 시작main → run_server

    옵션을 읽고, 끊긴 연결에 쓰다가 죽지 않도록 SIGPIPE를 무시합니다. SIGINT·SIGTERM은 종료 플래그만 세웁니다. 듣기 소켓을 논블로킹으로 열고 워커 8개를 만듭니다.

  2. 연결 수락poll → accept → setsockopt(TCP_NODELAY)

    메인 스레드는 poll()로 새 연결을 기다리다 accept()로 꺼냅니다. 작은 응답이 지연되지 않게 Nagle 알고리즘을 끄고, 연결을 블로킹 모드로 되돌립니다.

  3. 대기열에 넣기threadpool_submit

    연결 번호(fd)를 링 버퍼에 넣고 조건 변수로 잠든 워커 하나를 깨웁니다. 버퍼가 가득 차면 이 자리에서 503을 보냅니다.

  4. 워커가 연결을 맡음worker → handle_connection

    워커는 연결을 닫을 때까지 이 연결만 처리합니다. keep-alive면 같은 연결에서 다음 요청을 반복해서 읽습니다.

  5. 요청 읽기와 해석read_request → parse_request_line / parse_header_line

    8KB 버퍼(RIO)로 소켓을 읽어 요청 줄, 헤더, 본문을 구조체 http_request에 채웁니다. 크기·시간 상한을 넘으면 오류 상태 코드를 돌려줍니다.

  6. 처리기 고르기dispatch

    절대 URI인지, 라우팅 규칙과 맞는지, /cgi-bin/인지를 차례로 보고 처리기를 고릅니다. 아래 시뮬레이터에서 직접 시험해 볼 수 있습니다.

  7. 응답 보내기serve_static_at → send_headers → send_until

    파일을 안전하게 열고, 상태 줄과 헤더를 보낸 뒤 8KB씩 읽어 소켓에 씁니다.

  8. 마무리finish_request → access_finish → close

    처리기가 돌려준 값이 오류 코드면 오류 응답을 대신 보냅니다. -v 옵션이면 접근 로그 한 줄을 남기고, 연결을 유지하지 않으면 닫습니다.

동시성

스레드 풀과 워커 양보

메인 스레드(생산자)가 연결을 원형 대기열에 넣고, 워커(소비자)가 하나씩 꺼냅니다. 대기열은 head·tail 두 위치만 움직이는 고정 크기 배열이라 메모리를 새로 할당하지 않습니다. 대기열은 뮤텍스 하나로 보호하고, 비어 있으면 워커는 조건 변수에서 잠듭니다.

대기열 (축소 모형: 칸 6개 · 실제 기본값 1024)
워커 (축소 모형: 4개 · 실제 기본값 8)

초록은 요청 처리 중, 파랑은 응답을 보낸 뒤 같은 연결의 다음 요청을 기다리는(keep-alive) 상태입니다. 대기열에 연결이 있으면 파란 워커는 잠깐(실제 100ms) 기다린 뒤 연결을 닫고 다음 연결을 맡습니다.

양보를 결정하는 한 줄

threadpool_has_waiting()은 count > idle을 돌려줍니다. 대기열에 든 연결 수가 잠든 워커 수보다 많으면 "누군가 진짜로 기다리고 있다"는 뜻입니다. 막 깨어나는 중인 워커가 가져갈 연결은 대기로 세지 않습니다.

양보는 두 곳에서 일어납니다. 응답을 보내기 직전에 기다리는 연결이 있으면 그 응답을 Connection: close로 보내고, 다음 요청을 기다리는 유휴 연결은 100ms 이상 조용하면 닫습니다.

왜 양보가 필요한가

워커가 8개인데 keep-alive 연결이 9개면, 아홉 번째는 누군가 5초 타임아웃으로 끊길 때까지 기다려야 합니다. 양보가 있으면 그 대기가 사라지는 대신 연결 재사용의 이득이 줄어듭니다. 아래 부하 측정에서 동시 연결 8개 → 9개 구간의 처리량 변화가 이 효과입니다.

연결을 닫는 순서: 그냥 close()하면 응답을 잃는다

읽지 않은 데이터가 남은 소켓을 닫으면 커널은 FIN 대신 RST를 보냅니다. 클라이언트는 RST를 받는 순간 아직 읽지 않은 응답까지 버릴 수 있습니다. 그래서 서버는 송신만 먼저 닫고 남은 입력을 잠깐 버린 뒤 닫습니다(linger_close_input).

시간 예산

느린 상대가 워커를 붙잡지 못하게

워커 수가 정해져 있으므로, 한 연결이 워커를 오래 붙잡으면 다른 손님이 기다립니다. 그래서 모든 읽기·쓰기·연결에 마감 시각을 붙였습니다. 마감은 "지금부터 몇 초"가 아니라 CLOCK_MONOTONIC 기준의 절대 시각(밀리초)으로 저장합니다. 데이터가 1바이트씩 조금씩 와도 마감이 뒤로 밀리지 않습니다.

종료 마감과 합치기

모든 대기 함수는 실제 마감으로 effective_deadline(end)를 씁니다. 평소에는 각자의 마감이 그대로 쓰이고, 종료 신호를 받으면 "지금 + 5초"인 종료 마감과 비교해 더 이른 쪽을 씁니다. 그래서 30초짜리 중계도 종료 중에는 5초 안에 정리됩니다.

실제 마감 = min(각자의 마감, 종료 마감)

예산 나눠 쓰기

프록시는 DNS 조회부터 응답 헤더까지 5초를 한 번에 받습니다. 백엔드 후보가 2개면 첫 후보에 남은 시간의 절반(2.5초)만 주고, 실패하면 남은 시간을 아직 시도하지 않은 후보 수로 다시 나눕니다. 한 이름이 여러 IP로 풀릴 때도 같은 방식입니다.

RIO: 적게 읽혀도 괜찮게

TCP에서 read()는 요청한 양보다 적게 돌려줄 수 있습니다(short count). RIO는 한 번에 최대 8KB를 내부 버퍼로 받아 두고, 줄 단위·바이트 수 단위로 조금씩 꺼내 줍니다. 쓰기 쪽 rio_writen·send_until은 전부 보낼 때까지 반복합니다.

보내기

확장자로 Content-Type을 정하고(.html → text/html, 모르면 application/octet-stream), 파일 크기를 Content-Length로 보낸 뒤 8KB씩 읽어 씁니다. HEAD는 헤더만, POST는 405입니다. 응답 헤더에는 Date가 함께 들어갑니다.

왜 경로 문자열이 아니라 fd로 다시 여나

경로를 검사한 순간과 여는 순간 사이에 누군가 폴더를 링크로 바꾸면 검사가 무의미해집니다. 서버는 시작할 때 루트 폴더를 미리 열어 두고(init_local_root), 그 fd 아래에서만 파일을 엽니다. 검사와 열기가 같은 기준을 보게 됩니다.

CGI

다른 프로그램을 실행해 그 출력을 응답으로

/cgi-bin/으로 시작하는 요청은 해당 실행 파일을 새 프로세스로 띄웁니다. 요청 정보는 환경 변수로, 본문은 표준 입력으로 주고, 프로그램이 표준 출력에 쓴 내용을 클라이언트에게 중계합니다. 예제 adder는 a=1&b=2를 받아 3을 출력합니다.

CGI 응답 뒤에는 언제 연결을 재사용할까?

예제 adder는 Content-Length로 본문의 길이를 알려 줍니다. 요청과 워커가 연결 유지를 허용하면 그 길이만큼 보낸 뒤 같은 연결에서 다음 요청을 받습니다. CGI가 길이를 생략하거나 Connection: close를 출력하면 응답 후 연결을 닫습니다.

왜 프로세스 그룹인가

CGI가 또 다른 프로그램을 띄웠다면, 자식만 죽여서는 손자가 남습니다. 요청마다 새 그룹을 만들고 그룹 전체에 신호를 보내 한 번에 정리합니다.

프록시

두 개의 연결을 이어 주는 중계자

프록시는 클라이언트와의 연결, 백엔드와의 연결 두 개를 잡고 요청을 앞으로, 응답을 뒤로 옮깁니다. 두 방식의 차이는 "누가 목적지를 정하느냐"입니다.

백엔드 상태를 바꾸고 요청을 보내 보세요. select_backend·finish_backend·reverse_proxy_until의 규칙을 옮긴 모형이며, 아래 로그는 -v 옵션의 접근 로그 형식입니다.

연결 거부

백엔드가 꺼져 있으면 즉시 다음 후보로 넘어갑니다. 거부는 제외 기간을 만들지 않으므로 서버가 다시 켜지면 다음 요청부터 바로 쓰입니다. 모두 거부하면 502.

응답 없음

자기 몫의 시간(2.5초)을 다 쓰고 다음 후보로 넘어가며, 이 백엔드를 5초간 제외합니다. 제외가 끝나면 요청 하나가 먼저 복구를 확인합니다. 전체 5초를 넘기면 504.

재시도하지 않는 경우

연결에 성공해 요청을 보내기 시작했다면 실패해도 다른 백엔드로 다시 보내지 않습니다. POST가 두 번 실행되는 일을 막기 위해서입니다.

백엔드로 보낼 때 헤더가 바뀌는 방식

연결 하나 구간에서만 의미가 있는 헤더(hop-by-hop)는 지우고, 프록시가 알게 된 정보를 더합니다.

클라이언트 → 이 서버 → 백엔드 (127.0.0.1:8001)
GET /api/users?page=2 HTTP/1.1
Host: 127.0.0.1:8080
Accept: application/json
- Connection: keep-alive 연결 단위 헤더 삭제
- Keep-Alive: timeout=5 Proxy-*, TE, Upgrade, Expect 등도 삭제
- X-Forwarded-For: 6.6.6.6 클라이언트가 보낸 값은 믿지 않음
+ X-Forwarded-For: 127.0.0.1 실제 TCP 상대 주소
+ X-Forwarded-Proto: http
+ Via: 1.1 127.0.0.1:8080 (w13-<무작위 128비트>)
+ Connection: close
무한 루프 막기. 서버는 시작할 때 /dev/urandom으로 자기 식별자를 만들어 Via에 넣습니다. 요청의 Via에서 자기 식별자나 자기 주소를 다시 발견하면, 또는 백엔드 주소가 자기 자신이면 요청을 보내지 않고 508 Loop Detected로 끝냅니다. 설정 실수로 프록시가 자기 자신을 가리켜도 요청이 끝없이 돌지 않습니다.

마감이 있는 DNS 조회

getaddrinfo()에는 시간 제한이 없습니다. 그래서 조회를 별도 스레드(분리 스레드)에 맡기고, 워커는 조건 변수에서 마감까지만 기다립니다. 마감이 지나면 결과를 포기하고, 늦게 끝난 조회 스레드가 메모리를 직접 정리합니다. 동시에 도는 조회는 최대 8개로 제한합니다.

워커→ 생성 →조회 스레드→ 결과 →조건 변수 깨움

응답 중계 (response_stream.c)

백엔드·CGI의 응답을 그대로 흘려보내지 않고 상태 줄과 헤더를 먼저 검사합니다. 103 같은 중간 응답은 최종 응답보다 먼저 전달하고, chunked 응답은 인코딩을 유지한 채 조각 단위로 옮깁니다. 응답에도 Via를 붙이고, 중계 전체에 30초, 멈춤에 5초 상한을 둡니다.

커밋 3a6b120, Windows Docker(gcc:14) 컨테이너 한 곳에서 서버와 ApacheBench를 함께 실행, 기본 설정(워커 8, 큐 1024), 319바이트 /index.html, 요청 5,000건, 조건마다 1회. 클라이언트와 CPU를 나눠 쓰므로 절대값보다 경향을 보는 자료입니다. 모든 조건에서 실패 0건.

keep-alive는 연결 수가 워커 수(8)와 같을 때 가장 빠릅니다(38,253건/초). 9개부터는 남는 연결에 워커를 넘겨주느라 연결을 닫게 되어, 재사용 없음과 비슷한 수준(약 1만~1만 2천 건/초)으로 내려갑니다. 대신 어떤 연결도 5초 타임아웃만큼 멈춰 서지 않습니다.
